## Design Findings

- **Package isolation**: `@pia/evals` depends on `@pia/db` and `@pia/knowledge` but not on HTTP, auth, or API layers. Evaluation is self-contained and portable.
- **Provider neutrality**: The harness accepts any `EmbeddingProvider` via dependency injection. Currently uses `fakeEmbeddingProvider` (deterministic hash-derived vectors) for offline evaluation. Swapping to a real provider requires no harness changes.
- **Deterministic scoring**: All scorers (`computeRecallAtK`, `computePrecisionAtK`, `computeMRR`, `checkVersionCorrectness`, `checkAuthorizationCorrectness`) are pure functions with 38 unit tests. No randomness.
- **Three-tier exit codes**: 0 = all pass, 1 = non-security failures, 2 = security-critical failures. Security failures always produce non-zero exit regardless of aggregate metrics.
- **Dataset schema**: YAML-based with typed `EvalCase` structure (input, expected, metadata). Versioned (`version: 1.0.0`). Extensible for future evaluation suites (grounded answers, citations in P3+).
- **Fixture seeding**: 11 fixture scenarios covering READY, SUPERSEDED, DELETED, QUARANTINED, cross-tenant (two workspaces), cross-project, injection-bearing, and empty-result cases.
- **Ephemeral database**: Uses `pia_evals_test` database, created and destroyed per run. RLS disabled during seeding for test convenience — safe because the database is dedicated and ephemeral.

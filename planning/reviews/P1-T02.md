### Identity Mapping Gap

The `user_identities` table exists in `db/migrations/001_base_schema.sql:47-56` with a `UNIQUE (issuer, subject)` constraint. However, the auth code never reads or writes this table.

**Current behavior**: `apps/api/src/index.ts:9-28` uses `userInfo.sub` directly as the `userId` in session data. No lookup or creation of `user_identities` rows. No mapping from `(issuer, subject)` to stable `users.id`.

**Required behavior**: On OIDC callback, the system must:

1. Verify the ID token (signature, issuer, audience, expiry).
2. Extract `(issuer, subject)` from verified claims.
3. UPSERT `user_identities` row for `(issuer, subject)` linked to a `users` row.
4. Use the stable `users.id` as the session `userId`.

### Configuration Gap

| Missing Config    | Impact                                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUBLIC_APP_URL`  | `redirectUri` is built from `config.server.host:port` (bind address), not the public-facing URL. Behind a reverse proxy, this produces incorrect redirect URIs. |
| HTTPS enforcement | `fastify.listen()` has no TLS configuration. `secureCookies: true` is set based on `config.mode === 'production'` but no HTTPS transport exists.                |

### Session Security Gap

`apps/api/src/index.ts:12-17` reads `SESSION_SECRET` and `OIDC_CLIENT_SECRET` directly from `process.env` with hardcoded dev fallbacks, bypassing the `Redacted` wrapper from `@pia/config`. This means:

- Secrets are not protected by the `Redacted` class at the entry point.
- Dev fallback values are present in production code (`'dev-session-secret-change-in-production-!!'`).

### AC3: GET /messages has real cursor pagination, or the endpoint contract explicitly avoids silent truncation

**PASS** — Verified through source inspection:

- `apps/api/src/routes/conversations.ts` L222–244:
  - Optional `?cursor=<base64url>` and `?limit=<n>` query parameters accepted.
  - `decodeCursor(reqQuery.cursor)` (from `@pia/contracts`) extracts the `before` message ID. Returns `undefined` on invalid input → first-page fetch (fail-safe).

- Previously the endpoint hardcoded `limit: 200` with `next_cursor: null`, silently dropping messages beyond 200.
- `api/openapi.yaml` updated (L400–402) to document the cursor and limit parameters, referencing shared parameter components already used by seven other paginated endpoints.
- Backward-compatible: clients not sending `cursor` receive the first page identically to the old behavior.

## Defects

1. **Run-record formatting (P3)**: `planning/runs/P3-T11.md` has Prettier formatting issues causing `pnpm format:check` to exit with code 1. This is a documentation artifact — all four product source files pass formatting. Non-blocking; a follow-up `pnpm format:fix` on the run record resolves it.

2. **`data-streaming-run` attribute vs `loadMessages()` rewrite (P2)** — When `loadMessages()` rewrites `thread.innerHTML` (conversation-detail.ts L77), it destroys any active streaming element bearing `data-streaming-run`. A simultaneous streaming run and page load will conflict. This is a pre-existing architectural limitation of the inline-CSS/JS approach, acknowledged in the run record, and not introduced by this task.

3. **Client-side cursor pagination not implemented (P2)** — The server now supports cursor pagination, but `loadMessages()` in conversation-detail.ts does not yet use it — it fetches a single initial page. For conversations with >200 messages, older messages remain unreachable by the client. Requires a separate UI iteration (acknowledged in run record).

4. **OpenAPI Limit component mismatch (P3)** — The shared `Limit` component (`maximum: 100, default: 25`) does not match the route's actual limits (`MAX_PAGE_LIMIT: 200, DEFAULT_PAGE_LIMIT: 50`). This is a pre-existing inconsistency across all paginated endpoints, not introduced here.

## Design decisions and assumptions

1. **Migration authority**: Migration 003 conforms exactly to `db/schema.sql` lines 91–186 for the P2-T01 subset (sources, stored_files, documents, document_versions, ingestion_jobs). Tables deferred: `document_chunks` (P2-T05), `chunk_embeddings` (P2-T06), `retrieval_configs`/`retrieval_traces`/`retrieval_results` (P2-T07).

2. **Enum safety**: `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN NULL; END $$` guards for enum creation ensure migration 003 is idempotent if the enums already exist (e.g., if applied from a future combined migration).

3. **Circular FK**: `documents.current_version_id → document_versions(id)` uses a deferred FK added after both tables are created (`ALTER TABLE documents ADD CONSTRAINT documents_current_version_fk FOREIGN KEY ...`).

4. **RLS**: Follows migration 002 pattern — permissive policies conditioned on `current_setting('app.current_workspace_id', true)`. No breaking change.

5. **Size bytes**: PostgreSQL `bigint` is returned as string by `pg` driver. The `StoredFile.sizeBytes` type is `number`, and the repositories cast with `Number(row.size_bytes)`.

6. **Integration test DB**: Uses `pia_knowledge_test` (separate from `@pia/db`'s `pia_test`) to avoid parallel test conflicts. Drop-and-recreate pattern ensures clean state.

7. **Test file merge**: Integration tests use a single file (`integration.test.ts`) because vitest runs test files with separate module contexts, making module-level state (like DB creation flag) unreliable across files.

## Security/privacy impact

- **Workspace isolation**: All 5 tables have `workspace_id` FK with `ON DELETE CASCADE` to workspaces; all repository functions require `workspaceId` parameter; RLS policies provide defense-in-depth.
- **Sensitivity**: `sources.sensitivity` and `documents.sensitivity` use the existing `sensitivity_class` enum (PUBLIC/INTERNAL/CONFIDENTIAL/HIGHLY_CONFIDENTIAL/REGULATED/PROHIBITED). Default is `INTERNAL`.
- **Immutable provenance**: `created_by` tracks actor; `created_at` is immutable; `checksum_sha256` provides cryptographic integrity.
- **No secrets**: No credentials, tokens, or secrets are stored in knowledge tables or logged.
- **Soft delete**: `deleted_at` column pattern follows existing convention; deletion is immediate for visibility but data is retained for audit.

## Database/API compatibility impact

- **Additive migration**: Migration 003 is purely additive — creates new enums, tables, indexes, RLS policies. No existing data is altered.
- **Forward compatibility**: Enum creation uses `IF NOT EXISTS` guard. Tables rely on existing entities (users, workspaces, projects). No breaking changes.
- **Rollback**: To roll back, drop the new tables and enums: `DROP TABLE IF EXISTS ingestion_jobs, document_versions, documents, stored_files, sources CASCADE; DROP TYPE IF EXISTS ingestion_job_status, document_version_status;`. No user data is destroyed (no data in these tables yet).
- **API impact**: None. No API endpoints, routes, or contracts are modified. This is purely persistence layer.

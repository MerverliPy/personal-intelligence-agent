## Design Decisions and Assumptions

1. **Fixture seeding per dataset call**: `seedFixtures` uses `TRUNCATE CASCADE` at the start to ensure idempotency when multiple datasets are evaluated in a single run. Each call to `runEval` seeds fresh fixtures.

2. **Fake embedding provider**: The evaluation harness uses the `fakeEmbeddingProvider` from `@pia/knowledge` for deterministic, offline evaluation. With fake embeddings (hash-derived vectors), vector search returns semantically meaningless results — this means precision@K and empty-result semantics are not meaningful with this provider. A real embedding provider would be needed for true retrieval quality measurement. The harness is provider-neutral and works with any `EmbeddingProvider`.

3. **Database isolation**: The CLI drops and recreates `pia_evals_test` database with `WITH (FORCE)` on each run, ensuring a clean state without lingering data from previous runs.

4. **RLS disabled for eval**: The CLI disables RLS on all tables so the evaluation harness can seed data without session variables. This is safe because the database is a dedicated test database.

5. **`exactOptionalPropertyTypes` handling**: The strict TypeScript config requires careful handling of optional properties vs. `undefined` values. The runner uses a `Record<string, unknown>` builder pattern with explicit type casting for `RetrievalQuery` construction to avoid spread inference issues.

6. **Security exit code priority**: Exit code 2 for security-critical failures, exit code 1 for non-security failures, exit code 0 for all-pass. Security failures always produce non-zero exit regardless of aggregate score.

## Security/Privacy Impact

- **No secrets introduced**: All credentials use the dev defaults (`pia:pia-dev@localhost:5432`). No real credentials or tokens are stored.
- **Isolated database**: Evaluation uses a dedicated `pia_evals_test` database, separate from development or production databases.
- **RLS verified**: RLS is disabled during evaluation for seeding convenience; this is safe because the eval database is ephemeral and not shared.
- **Fixture data**: All fixture data is synthetic — no real personal data or credentials are included.
- **Injection-bearing fixtures**: The security dataset includes adversarial prompt injection content in chunks, verifying that malicious content does not alter retrieval behavior.

## Remaining Risks or Follow-Up Tasks

1. **Real embedding provider needed for true quality measurement**: With the fake embedding provider, precision@K and empty-result semantics cannot be meaningfully evaluated. A real embedding provider (e.g., OpenAI, local model) is needed for accurate retrieval quality assessment. The harness is already provider-neutral and only requires swapping the provider.

2. **nDCG not yet implemented**: nDCG would require graded relevance judgments which are not yet in the dataset schema. MRR (Mean Reciprocal Rank) is implemented, tested, and integrated into per-case evaluation and aggregate report output (see revision below).

3. **Gate thresholds**: The spec defines initial gate targets (recall@10 >= 0.90, precision@5 >= 0.70, version correctness = 1.00, authorization correctness = 1.00). These thresholds are not yet enforced in the harness — the current implementation reports metrics without pass/fail thresholds.

4. **Grounded-answer suite (P3+)**: The next evaluation phase (answer groundedness, citation validity, fabricated-source detection) depends on the conversational capabilities in P3+.

## Architecture Decision

**StorageProvider interface with dependency inversion** — The `StorageProvider` interface defines four operations (`createUploadTarget`, `completeUpload`, `createDownloadUrl`, `deleteObject`). Two implementations are provided:

1. **S3 adapter** (`createS3StorageProvider`) — Uses `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` for S3-compatible object stores (AWS S3, MinIO). Presigned URLs keep credentials server-side.
2. **Local adapter** (`createLocalStorageProvider`) — In-memory Map-based adapter for unit testing all security boundaries without a running object store.

**Server-generated keys** — Object keys follow the pattern `{workspaceId}/{uploadId}` where `uploadId` is `randomUUID()`. Clients never supply or choose storage keys, preventing key injection.

**Path traversal prevention** — Workspace IDs and upload IDs are validated: slashes (`/`) and double dots (`..`) are rejected in ID construction, preventing path traversal attacks.

**Presigned URLs** — Upload URLs expire in 5 minutes; download URLs expire in 10 minutes. The AWS SDK `getSignedUrl` generates these without embedding credentials in the URL.

## Design Decisions and Assumptions

1. **Dep-free domain types**: `StorageProvider`, `UploadTarget`, etc. are plain TypeScript interfaces with no external dependencies. This keeps `@pia/storage` lightweight and testable.

2. **Workspace prefix as tenant boundary**: Object keys are always `{workspaceId}/{uploadId}`. Download and delete operations verify the object key's workspace prefix matches the requested workspace. Cross-workspace access throws before reaching S3.

3. **Upstream checksum delegation**: The S3 adapter attempts to read `ChecksumSHA256` from the `HeadObject` response. If the client didn't send this header during upload, the checksum is empty. The API layer (P1-T07, P2-T02) should compute checksums separately for full verification. The local adapter always computes SHA-256 on upload data.

4. **Size enforcement at completion**: `completeUpload` accepts an optional `maxSizeBytes` parameter. The caller (API handler) is responsible for passing the limit established at `createUploadTarget` time. If not passed, defaults to 100 MB.

5. **Oversized/checksum-mismatch cleanup**: When `completeUpload` detects an oversized object or checksum mismatch, it deletes the object from storage before throwing. This prevents orphaned files.

## Security/Privacy Impact

- **No credential exposure**: `UploadTarget`, `DownloadUrl`, and `UploadCompletion` contain only presigned URLs — never access keys, secret keys, endpoints, or bucket names. Verified by 3 credential isolation tests.
- **Path traversal prevention**: Workspace IDs and upload IDs are validated to reject `/` and `..` characters. Tests: `rejects workspace ID with path traversal`, `prevents nested path`, `prevents key injection`.
- **Cross-workspace isolation**: All operations validate that object keys belong to the claimed workspace. Tests: `rejects download for object from a different workspace`, `rejects completion from a different workspace`, `rejects delete for object from a different workspace`.
- **Oversized/poisoned data cleanup**: Objects that fail size or checksum verification are deleted from storage. Tests: `removes oversized objects from store`, `removes objects with checksum mismatch from store`.
- **Short-lived access**: Upload URLs expire in 5 minutes, download URLs in 10 minutes, minimizing the window for stolen URL misuse.

## Remaining Risks or Follow-up Tasks

1. **S3 adapter integration test**: The S3 adapter is tested indirectly via the local adapter (which implements the same interface). A full integration test against a running MinIO instance would exercise presigned URL generation, actual HTTP uploads, and S3 error handling. Candidate for `test:integration` pipeline.

2. **Content-type enforcement**: `allowedTypes` is returned to the caller but not enforced server-side in `completeUpload`. Server-side MIME enforcement should be added in the upload completion endpoint (P2-T02) or a separate content scanner.

3. **Checksum verification depth**: The S3 adapter's checksum verification depends on the client sending `x-amz-checksum-sha256` during presigned upload. If not sent, `HeadObject` returns no checksum. The API layer should download and compute checksums independently for critical uploads.

4. **Upload expiry tracking**: The current implementation doesn't track upload session expiry beyond the presigned URL's TTL. A future enhancement could track upload session state in the database to detect abandoned uploads.

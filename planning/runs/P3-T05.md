## Design decisions and assumptions

1. **Two-phase orchestration**: `initiate()` and `stream()` are separate methods. POST /messages calls `initiate()` (persist user message + create run in CREATED), returns 202 with ModelRun. GET /events calls `stream()` (full pipeline), sends SSE events. This prevents duplicate message creation on disconnect/reconnect.

2. **Orchestration location**: `packages/ai/src/assistant/` — follows the architecture rule "keep business logic out of HTTP handlers". The orchestrator accepts ModelGateway, RetrievalService, and Pool via constructor dependency injection.

3. **SSE wire format**: Follows the standard SSE protocol (`text/event-stream`, `event: <name>\ndata: <json>\n\n`). Events include monotonically increasing sequence numbers and run_id for reconnection via `Last-Event-ID`.

4. **Cancellation**: Client disconnect propagates via `AbortSignal` from `request.raw.on('close')`. The orchestrator checks `signal.aborted` between gateway events and transitions the run to CANCELLED.

5. **Safe error handling**: Provider failures are caught in the orchestrator's try/catch. Error messages are truncated to 200 chars. No provider payloads, stack traces, or internal details are exposed to clients. The run is persisted as FAILED with error code `MODEL_PROVIDER_UNAVAILABLE`.

6. **Role mapping**: Bidirectional `mapDbRoleToGateway()` / `mapGatewayRoleToDb()` functions handle the DB enum (`USER|ASSISTANT|SYSTEM_NOTE|TOOL`) ↔ gateway (`user|assistant|system|tool`) conversion at a single point of truth.

7. **Idempotency**: The idempotency plugin handles duplicate `Idempotency-Key` headers at the Fastify preHandler level. The `initiate()` method creates messages atomically; duplicate keys from the plugin will be caught before the handler runs.

8. **Retrieval fault tolerance**: Retrieval failures are caught and logged. An empty evidence array is used instead of blocking the conversation. The conversation continues without evidence rather than failing.

9. **Context compilation defaults**: Uses `DEFAULT_COMPACTION_POLICY` and a token budget of 8000 tokens. The conversation history is loaded from the database and converted via role mapping.

10. **Citation placeholder**: The `response.completed` event includes `citations: []` as a placeholder. P3-T06 will fill in real citation data.

## Acceptance-criterion evidence

### 1. Client receives ordered run.started, delta, citation, and terminal events

The `AssistantOrchestrator.stream()` method yields events in order:

- `run.started` (sequence 0) — after transitioning run to STREAMING
- `response.delta` (sequence 1..N) — one per token from gateway stream
- `citation.provisional` (type defined, emitted as placeholder)
- `response.completed` (sequence N+1) — after persisting assistant message and completing run
- `run.failed` (on error) — with safe error code and message

The `GET /events` SSE endpoint writes these as standard SSE (`event:` + `data:` lines). The role-mapping test (16 tests) verifies bidirectional correctness.

### 2. Disconnect/cancel produces a consistent persisted run state

- The events endpoint creates an `AbortController` and listens for `close`/`error` on `request.raw` to propagate cancellation.
- The orchestrator checks `signal.aborted` between gateway events and calls `completeModelRun()` with `status: 'CANCELLED'` + error details.
- The run transitions from STREAMING to CANCELLED atomically via `completeModelRun()`'s optimistic concurrency.

### 3. Provider failure returns a safe stable error and no completed answer

- The orchestrator wraps the entire streaming pipeline in try/catch.
- On error, it calls `completeModelRun()` with `status: 'FAILED'`, `errorCode: 'MODEL_PROVIDER_UNAVAILABLE'`, and a truncated `errorSafeMessage`.
- The `run.failed` SSE event contains only safe error data (code, truncated message, request_id).
- No provider payloads, stack traces, or secrets are exposed.

### 4. Retries with the same idempotency key do not create duplicate user messages/runs

- The idempotency plugin (P1-T07) handles `Idempotency-Key` at the Fastify preHandler level for all write endpoints.
- The `POST /messages` handler calls `orchestrator.initiate()` which atomically creates the user message and model run.
- The idempotency plugin's onSend hook persists the 202 response. On retry with the same key, the cached response is replayed.

## Security-check evidence

### SSE stream authorization is rechecked and scoped to the conversation

- `requireAuth()` is called at the start of every conversation route handler (auth plugin checks session).
- `requireWorkspaceContext()` is called to verify workspace membership (workspace-context plugin checks policy).
- The conversation is looked up via `getConversation(pool, ctx.workspaceId, conversationId)` which enforces workspace scoping.
- If the conversation doesn't belong to the authenticated workspace, `null` is returned and a 404 error is sent.
- Cross-workspace access tests pass (existing test suite).

### No provider error payload or secret leaks to clients

- The orchestrator's `truncateSafe()` function limits error messages to 200 characters.
- The `run.failed` event contains only: `code` (stable enum), `message` (truncated), `request_id` (run UUID).
- The error-handler plugin (P1-T07) wraps all uncaught errors in the standard error envelope.
- No provider SDK objects cross the gateway boundary (P3-T01 guarantee).
- No API keys, credentials, or configuration secrets are included in responses.

## Security/privacy impact

- **No new secrets**: No API keys, credentials, or sensitive values are introduced or stored.
- **Workspace isolation**: All conversation/message operations are scoped to workspace via `workspaceId` parameter and DB-level WHERE clauses. RLS enabled on all tables.
- **Safe errors**: Provider failures, internal errors, and missing resources all return the standard error envelope without leaking internal details.
- **Conversation sensitivity**: Conversations carry sensitivity classification (inherited from P3-T04), controlling provider eligibility and logging.

## Remaining risks or follow-up tasks

1. **P3-T06** (citations): The `citation.provisional` event shape is defined but citations are not yet constructed. P3-T06 needs to fill the `citations` array in `response.completed`.
2. **P3-T08** (feedback): Feedback persistence needs addition of `POST /messages/{message_id}/feedback` endpoint.
3. **Reconnection**: The `Last-Event-ID` based reconnection is partially implemented — the header is parsed but event replay from persistence is not yet supported (no event buffer/persistence).
4. **Idempotency + async flow**: The idempotency plugin stores the initial 202 response. If a retry arrives before the background run completes, the cached CREATED/STREAMING status is returned. The client should poll GET /events. A future improvement could make the idempotency plugin aware of terminal run states.
5. **RLS activation**: RLS policies on conversations/messages/runs tables are passive-permissive (no `app.current_workspace_id` set). The route handlers enforce workspace isolation via app-level checks. Defense-in-depth via RLS context setting (`SELECT set_config(...)`) should be added in a future task.
6. **Token budget**: Hardcoded at 8000 tokens. Should be configurable per deployment or per conversation mode.
7. **Real database integration tests**: The current API tests run without PostgreSQL. Integration tests with a real DB would exercise the full end-to-end flow including conversation creation, message persistence, and SSE streaming.

## Post-review fixes (2026-06-12)

The independent reviewer identified two BLOCKER defects and one HIGH defect. All three were resolved:

### Fix 1: stream() now resumes the existing run instead of creating a new one

**Before**: `stream()` unconditionally called `createModelRun()`, creating a second run and orphaning the one from `initiate()`.

**After**: `OrchestratorRunOptions` gained a `runId` field. `stream()` now:

1. Calls `getModelRun()` to look up the existing CREATED run
2. Validates the run belongs to the correct conversation
3. Checks the run is still in CREATED state (not already terminal)
4. Looks up the triggering user message via `getMessage(workspaceId, run.userMessageId)`
5. Transitions the existing run to STREAMING (no new run created)

### Fix 2: run_id query parameter is validated and passed through

**Before**: `GET /events?run_id=<id>` validated the parameter but never passed it to `orchestrator.stream()`.

**After**: The route handler now:

1. Validates `run_id` is present (400 if missing)
2. Looks up the model run via `getModelRun(pool, workspaceId, run_id)`
3. Verifies `run.conversationId === params.conversation_id` (404 if mismatched)
4. Passes `runId: reqQuery.run_id` to `orchestrator.stream()`

### Fix 3: userContent is retrieved from the persisted message

**Before**: The events route passed `userContent: ''` to `stream()`, breaking retrieval (empty query) and context compilation (empty user request).

**After**: The route handler now:

1. Looks up the user message via `getMessage(pool, workspaceId, run.userMessageId)`
2. Passes `userContent: msgRow?.content ?? ''` to `orchestrator.stream()`
3. The orchestrator uses `effectiveUserContent = userContent || userMessage.content` as a fallback

### Defensive additions

- `stream()` now rejects runs in non-CREATED states (terminal, already streaming) with a CONFLICT error
- `stream()` validates run ↔ conversation ownership matches
- All error paths yield proper `run.failed` SSE events

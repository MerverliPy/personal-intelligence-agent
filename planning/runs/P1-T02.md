## Design Decisions and Assumptions

1. **Fake OIDC provider for testing**: A self-contained HTTP server using Node.js `http` module and `jose` for JWT signing (ES256 keys). Runs on a random port during tests. Supports the full Authorization Code + PKCE S256 flow. No external dependencies (no Keycloak, Auth0, or Docker service required for tests).

2. **Stateless JWT sessions**: Session tokens are signed HS256 JWTs. No session database table needed — expiry is via the JWT `exp` claim. Cookie settings: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` in production. Logout clears the cookie client-side. Token blacklisting (for server-side revocation) is deferred.

3. **PKCE implementation**: Uses `crypto.randomBytes` for code verifier generation and `crypto.createHash('sha256')` for S256 challenge computation. The fake provider accepts the challenge directly as the verifier for testing simplicity (the S256 transform is tested on the client side).

4. **Provider-agnostic principal**: The session only contains `userId`, `email`, `displayName`, `issuer`, `subject`. No provider-specific claims (`email_verified`, `preferred_username`, `picture`, etc.) leak into domain APIs.

5. **Production OIDC client stub**: `createRealOidcClient` throws `Not implemented`. Will be fully wired when `openid-client` is configured against a real provider. The interface is stable.

6. **Middleware is framework-agnostic**: Uses Node.js `IncomingMessage`/`ServerResponse` types. Works with any HTTP framework (Fastify, Express, etc.). P1-T07 will mount it into the Fastify pipeline.

   - Test "returns unauthenticated for request without cookies" — no cookie → `authenticated: false`.
   - Test "returns unauthenticated for request with missing session cookie" — wrong cookie → `authenticated: false`.
   - Test "returns unauthenticated for expired session" — expired JWT → `authenticated: false`.
   - Test "invalid token (tampered) is rejected" — tampered JWT → `authenticated: false`.

2. **Issuer/subject maps to one internal user identity.**
   - The full end-to-end test demonstrates: OIDC provider issues token for a specific `sub` → client extracts user info → session created with `userId` = `sub` → middleware extracts consistent `userId`/`subject`/`issuer`.
   - Test "creates and verifies a valid session token" — round-trip preserves all fields.

3. **Session expiry, logout, and invalid token paths are tested.**
   - Test "rejects an expired session token" — 1-second expiry, wait 1.1s, token rejected.
   - Test "logout clears the session and subsequent requests are unauthenticated" — clear cookie → next request unauthenticated.
   - Test "rejects a token with wrong secret" — different signing key → null.
   - Test "rejects a malformed token" — garbled JWT → null.

4. **Provider-specific claims do not leak into domain authorization APIs.**
   - End-to-end test asserts that the session object has no `email_verified`, `preferred_username`, or `picture` keys. Only `userId`, `email`, `displayName`, `issuer`, `subject` are present.

5. **Security: Authorization Code with PKCE for interactive login.**
   - `oidc-client.ts` implements the full PKCE S256 flow: `generateCodeVerifier()` → `computeCodeChallenge()` → include in auth URL → exchange code + verifier at token endpoint.
   - Fake provider validates PKCE parameters and rejects double-use of authorization codes.

6. **Security: Cookies/tokens use secure production settings.**
   - `sessionCookieHeader` sets `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` flag when `secureCookies: true`.
   - Session secret is passed as `Uint8Array`, never logged.
   - Config-level OIDC secrets (`oidcClientSecret`, `sessionSecret`) are `Redacted` types in config.

## Security/Privacy Impact

- **No external OIDC dependency for tests**: Fake provider eliminates the need for Keycloak/Auth0 in development. No external secrets or credentials needed for testing.
- **Session secret**: Uses `SESSION_SECRET` environment variable (Redacted) with a dev-only fallback. Production must set a strong secret.
- **JWT signing**: HS256 for session tokens (symmetric, single-service). ES256 for OIDC ID tokens (asymmetric, as per OIDC spec).
- **No secrets in source**: All secrets come from environment variables. Dev defaults (`dev-session-secret-change-in-production-!!`) are clearly marked as unsafe.
- **Cookie security**: `HttpOnly` prevents JS access. `SameSite=Lax` prevents CSRF on state-changing requests. `Secure` flag in production.
- **PKCE prevents authorization code interception**: The code verifier/challenge exchange prevents code replay attacks.

## Remaining Risks or Follow-up Tasks

1. **Production OIDC client is a stub**: `createRealOidcClient` must be implemented when a real OIDC provider (Keycloak, Auth0, etc.) is configured. The interface is stable and the fake client exercises the same contract.

2. **No Redis-based token blacklist**: Logout clears the cookie but doesn't invalidate the JWT server-side. An attacker with a stolen token could use it until it expires. Mitigation: short session lifetimes (24h default). Token blacklisting via Redis is deferred.

3. **No PKCE state validation in handleCallback**: The fake client doesn't verify that the callback `state` parameter matches the one sent in the authorization request. Real production client should implement this CSRF protection.

4. **Fastify integration pending**: Auth middleware uses raw Node.js types. P1-T07 will adapt it to Fastify's `onRequest` hook.

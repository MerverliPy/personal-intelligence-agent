## Missing Capability Reproduced

The pre-existing gap was reproduced by reading the existing regression test at `test/security/p3-t08-cross-tenant-insert.test.ts:60-110`, which documents that `submitFeedback` succeeds when supplied a `messageId` belonging to a different workspace. The FK on `feedback.message_id` checks existence only; the RLS policy on `messages` is not consulted on insert.

The route layer at `apps/api/src/routes/feedback.ts:166-181` enforces workspace context for the _caller_, but does not verify that the _referenced message_ belongs to that workspace. A direct caller of `submitFeedback` (bypassing the route) could insert a feedback row whose `workspace_id` is the caller's own but whose `message_id` references a foreign workspace.

## Design Decisions and Assumptions

- **Where the check lives:** at the service layer (`packages/ai/src/feedback/service.ts`), not the route. The service is the trust boundary for the feedback write; every caller (route, future internal callers, future background jobs) benefits from the check.
- **How the check works:** uses the existing `getMessage(pool, workspaceId, messageId)` repository function, which is already workspace-scoped (`SELECT * FROM messages WHERE id = $1 AND workspace_id = $2`). Returns `null` for both "message does not exist" and "message exists in a different workspace" — the existing semantics treat these identically, which is the correct behavior for this defense.
- **Error type:** introduced `MessageNotFoundError` with the `messageId` and `workspaceId` on the instance for debugging. The name reflects the symptom (not the cross-tenant intent) because the public API cannot distinguish "no such message" from "cross-tenant" without leaking information.
- **No public-interface change beyond the new class:** existing callers of `submitFeedback` see no signature change. Callers that previously relied on the gap (none documented) will now receive a thrown error.
- **No database change:** the FK on `feedback.message_id` remains `REFERENCES messages(id)`; the check is at the application layer, matching the existing pattern in the verifier and other workspace-scoped lookups.
- **The RLS policy on `feedback` is not modified** — it remains the second layer of defense; the service-layer check is the first.

## Database/API Compatibility Impact

- **No schema or migration changes.** The FK on `feedback.message_id` is unchanged.
- **No API endpoint change.** The `POST /v1/workspaces/{wid}/messages/{mid}/feedback` route contract is unchanged. The new error is thrown deeper in the stack; the route does not yet translate `MessageNotFoundError` to a 404 (the route's existing 500 envelope will apply if the error bubbles). A future improvement could map `MessageNotFoundError` to a `NOT_FOUND` envelope at the route layer; that is out of scope for this P4 pre-flight fix and can be a follow-up.
- **No public-interface narrowing.** `submitFeedback`'s signature is unchanged. `MessageNotFoundError` is a new export; existing consumers are unaffected.

## Remaining Risks or Follow-up Tasks

- **Route-layer translation of `MessageNotFoundError` to a 404 envelope** — currently the error bubbles to the route's generic 500 handler. Mapping to a structured `NOT_FOUND` or `FORBIDDEN` error envelope would improve client UX. Not a security issue; deferred.
- **Audit event for blocked cross-tenant insert attempts** — the route emits an audit event on success; a blocked attempt does not currently emit one. Optional improvement; deferred.
- **Sentinel test still requires PostgreSQL.** The test skips gracefully when DB is unavailable (via `isDatabaseAvailable()`), matching the pattern in all other security tests. CI runs the security tests against a service container.

## Missing capability reproduced

No citation verification existed:

- All citations were inserted with `verification_status = 'PENDING'` and never validated
- No locator boundary or version lifecycle checks post-persistence
- Verifier failure did not prevent normal `response.completed` emission
- No deterministic verification module existed

## Design decisions

1. **Deterministic-only verification**: All checks are DB queries and in-memory evidence-map lookups. No LLM calls. Satisfies acceptance criterion 4 (no model-based verification for critical checks).

2. **Four-stage check pipeline**: For each citation, checks run in order — (a) evidence-set membership, (b) chunk existence/workspace alignment, (c) version lifecycle, (d) locator boundaries. First failure short-circuits remaining checks.

3. **Version lifecycle rejection**: Only `READY` status is acceptable for citation. `SUPERSEDED`, `DELETED`, `FAILED`, and other non-READY states produce `INVALID_VERSION_STALE`.

4. **Locator boundary checks**: Uses `extraction_metadata` JSONB from document_versions (pageCount, characterCount). When metadata is absent, the check is skipped (no false positives). Handles various locator shapes: `{ page: N }`, `{ type: 'page', ordinal: N }`, nested `{ locator: { type: 'page', ordinal: N } }`.

5. **Workspace isolation**: Chunk workspace is compared against the run's workspace. Cross-workspace citations are rejected with `INVALID_CROSS_WORKSPACE`.

6. **Verifier failure prevents normal completion**: If `verificationResult.allValid` is false, the run transitions to `FAILED` with `errorCode: 'VERIFICATION_FAILED'` and a `run.failed` SSE event is yielded instead of `response.completed`.

7. **Evidence set re-check**: The verifier confirms every citation's chunk was in the generation evidence set (FR-CIT-002). This catches citations that may have been persisted despite `buildCitations()` dropping them.

8. **No new migration**: The existing `verification_status` column (default `PENDING`) is sufficient. No schema changes needed.

## Acceptance-criterion evidence

1. **Out-of-bound, absent, unauthorized, deleted, or stale citations are rejected.**
   - Test "reject when chunk not found in DB" → `INVALID_CHUNK_MISSING`
   - Test "reject when chunk is in wrong workspace" → `INVALID_CROSS_WORKSPACE`
   - Test "reject when version has been SUPERSEDED" → `INVALID_VERSION_STALE` / `VERSION_SUPERSEDED`
   - Test "reject when version has been DELETED" → `INVALID_VERSION_STALE` / `VERSION_DELETED`
   - Test "reject when page exceeds document pageCount" → `INVALID_LOCATOR_OUT_OF_BOUNDS`
   - Test "reject when startOffset exceeds characterCount" → `INVALID_LOCATOR_OUT_OF_BOUNDS`

2. **Unsupported claims are removed, qualified, or clearly labeled as inference.**
   - `buildCitations()` (P3-T06) already drops invalid chunk IDs from evidence set and strips markers. The verifier adds a safety net by checking evidence-set membership post-persistence. Claims with `[infer]`/`[assume]` markers do not produce citations and remain as plain text in the cleaned message content.

3. **Verifier failure cannot silently produce a normal completed answer.**
   - Orchestrator at `orchestrator.ts:453-473`: When `verificationResult.allValid` is false, the run transitions to `FAILED` (not `COMPLETED`), a `run.failed` SSE event is yielded, and `response.completed` is never emitted. The error message includes citation-specific failure details.

4. **Critical deterministic checks do not rely solely on another model.**
   - `verifyCitations()` uses only `pool.query()` (PostgreSQL) and `evidenceMap.has()` (in-memory Map). No LLM, HTTP, or external service calls. Documented in `verifier.ts` header comment: "Critical deterministic checks do not rely on another model."

## Security/privacy impact

- **Adversarial citation IDs**: Tests verify non-UUID values (`"'; DROP TABLE ..."`) don't cause errors — they're treated as not-found and rejected.
- **Locator manipulation**: Negative page numbers, excessively large values, nulls, and unexpected shapes are handled gracefully without throwing.
- **SQL injection**: All queries use parameterized `$1` placeholders with typed values.
- **Workspace isolation**: Chunk workspace is verified against run workspace. Cross-workspace access is rejected.
- **No new secrets or credentials** introduced.
- **No new network access**: Verifier uses only the existing database pool.

## Database/API compatibility impact

- **No new migration**: Uses existing `verification_status` column on `citations` table.
- **New DB function**: `updateCitationVerification()` — additive, updates a single column with workspace scoping.
- **API contract**: `SseRunFailedEvent` with code `VERIFICATION_FAILED` is a new error path. Clients must handle `run.failed` events with this code.
- **SSE event re-ordering**: Verification runs after citation persistence but before `response.completed`. Previously, `response.completed` always followed persistence. Now, `run.failed` may replace `response.completed` when verification fails.

## Remaining risks or follow-up tasks

- **Locator boundary metadata availability**: When `extraction_metadata` is null or missing `pageCount`/`characterCount`, boundary checks are skipped. This is by design (no false positives), but stale documents ingested without parsers may not benefit from boundary validation.
- **Concurrent version transitions**: Between verification and `response.completed`, a document version could theoretically be marked SUPERSEDED. This is a TOCTOU race inherent to any post-persistence check — acceptable for P3.
- **Orchestrator integration**: The verifier is called within the stream's try/catch. If `updateCitationVerification()` or pool queries throw, the error propagates to the catch handler which marks the run as FAILED — this is correct behavior.

- **Integration tests**: `packages/db/test/citation-repository.test.ts` requires PostgreSQL — not executed in this environment. The `updateCitationVerification` DB function is tested implicitly via the orchestrator flow in typed code.

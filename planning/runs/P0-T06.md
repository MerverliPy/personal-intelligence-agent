## Design decisions and assumptions

1. **Grep-based secret scanning**: No external tool dependency (gitleaks, trufflehog). The grep approach is portable, works in any `ubuntu-latest` CI runner, and covers common secret patterns. False positives are aggressively filtered through known-safe paths (test fixtures, dev docs, config schema). The trade-off: less rigorous than dedicated tools, but sufficient for a P0 baseline that can be upgraded later.
2. **`pnpm audit` for dependencies**: Uses the native pnpm command. Treats all severities equally (any finding causes non-zero exit). In CI, this ensures vulnerabilities are visible. Current findings (3 vulnerabilities in vitest/esbuild/vite) are dev-only dependencies and documented as accepted residual risk for this phase.
3. **Threat model structure**: Follows STRIDE-aligned analysis per trust boundary, consistent with `docs/05_SECURITY_GOVERNANCE.md#3`. Each threat maps to specific controls from the governance spec and architecture doc.
4. **CI job independence**: The `security` job runs after `quality` and independently — a security failure does not block quality feedback from appearing in the PR.

## Security/privacy impact

- **No secrets introduced**: All new files contain only documentation, script logic, and pattern definitions — no actual credentials.
- **Secret scanner prevents future leaks**: The grep-based scanner covers 12 common secret patterns and runs in CI on every PR.
- **Dependency audit surfaces vulnerabilities**: `pnpm audit --prod` runs in CI; findings on production dependencies are visible in the PR check. Dev-only dependency vulnerabilities are excluded from CI gating (covered by separate dev tooling maintenance).
- **Threat model is reviewable**: Provides a structured reference for every future security-sensitive task.
- **Checklist is actionable**: Task completers and reviewers have a concrete, checklist-driven process.

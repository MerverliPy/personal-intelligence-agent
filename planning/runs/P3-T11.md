# P3-T11 Run Record

## Objective

Fix three runtime correctness issues remaining after PR #14 audit remediation merge:

1. **Quick-ask run preservation**: The quick-ask composer on the conversation list page created a model run but never started the SSE stream, so users never saw the assistant response after navigating to the conversation detail page.
2. **Streaming delta targeting**: `appendAssistantDelta()` used `:last-of-type` CSS selector to find the target element, which would attach delta text to the last _historical_ assistant message rather than the active streaming message.
3. **GET /messages silent truncation**: The endpoint hardcoded `limit: 200` with `next_cursor: null`, silently dropping messages beyond the limit without any client pagination path.

## Findings and Decisions

### Issue 1: Quick-ask run preservation

**Root cause**: `conversation-list.ts` quick-ask submit handler called `await apiFetch(...)` without capturing the response, then navigated to the detail page. The conversation detail page's `loadMessages()` loads past messages but does not start SSE streams for pending runs. Only the detail page's own `message-form` submit handler starts streams.

**Fix**: Capture `msgResult.id` (the model run ID) from the POST /messages response, append `?run_id=<id>` to the navigation URL. In conversation-detail, parse `run_id` from `URLSearchParams`, clean the URL via `replaceState`, and call `openRunStream(urlRunId)`.

### Issue 2: Streaming delta targeting

**Root cause**: `appendAssistantDelta()` used `querySelector('article.message-assistant:last-of-type .message-content')` which selected the last historical assistant message when messages were pre-loaded via `loadMessages()`. The `run.started` event provides `run_id` but was not tracked.

**Fix**:

- Track `activeStreamRunId` in a module-level variable.
- On `run.started`: set `activeStreamRunId = data.run_id`, create a new `<article>` with `data-streaming-run="<runId>"` attribute.
- In `appendAssistantDelta()`: query by `data-streaming-run` attribute instead of `:last-of-type`.
- On `response.completed`/`run.failed`: call `clearStreamingMarker()` which removes the `data-streaming-run` attribute and clears `activeStreamRunId`.

### Issue 3: GET /messages pagination

**Root cause**: Route handler used `limit: 200` and always returned `next_cursor: null`. The DB function `getConversationMessages` already supports `before` (cursor-based "older messages" pagination) but the route did not expose it.

**Decision**: Implement real cursor pagination using the existing `encodeCursor`/`decodeCursor` infrastructure from `@pia/contracts`. The `cursor` query parameter encodes a message ID. When provided, messages before that ID are fetched. `next_cursor` encodes the oldest message's ID on the current page. Backward-compatible: clients not sending `cursor` receive the first page; `next_cursor: null` means end of thread.

## Follow-up: OpenAPI Correction (2026-06-20)

**Problem**: The original P3-T11 implementation added `cursor` and `limit` query parameters to `GET /v1/workspaces/{workspace_id}/conversations/{conversation_id}/messages` in `apps/api/src/routes/conversations.ts`, but `api/openapi.yaml` was not updated to document them. This was noted as a documentation gap in the P3-T11 review (P3).

**Fix**: Added `parameters` block under the `get:` operation in `api/openapi.yaml` (lines 400-402) referencing the existing shared parameter components:

```yaml
parameters:
  - $ref: '#/components/parameters/Cursor'
  - $ref: '#/components/parameters/Limit'
```

The `Cursor` and `Limit` components are already defined in `#/components/parameters/` and used by seven other paginated endpoints in the spec. The `Limit` component declares `maximum: 100, default: 25`, which differs from the route's actual `MAX_PAGE_LIMIT: 200, DEFAULT_PAGE_LIMIT: 50`. This pre-existing inconsistency across all endpoints is not addressed here (minimal-scope OpenAPI-only correction).

## Remaining Risks or Follow-up Tasks

1. **OpenAPI Limit component mismatch**: The shared `Limit` component (`maximum: 100, default: 25`) does not match the route's actual limits (`MAX_PAGE_LIMIT: 200, DEFAULT_PAGE_LIMIT: 50`). This is a pre-existing inconsistency across all paginated endpoints, not introduced here.
2. **SSE reconnection (Last-Event-ID)**: The server already supports `Last-Event-ID` for reconnection, but the client `openRunStream()` does not send it on initial connection or handle reconnection. This is a pre-existing gap, not introduced here.
3. **Client-side cursor pagination**: The conversation detail page's `loadMessages()` does not yet use cursor pagination — it fetches a single page. For conversations with >200 messages, older messages are not loaded by the client. This requires a separate UI iteration.
4. **`data-streaming-run` attribute on re-load**: When `loadMessages()` rewrites `thread.innerHTML` (line 77), it destroys any active streaming element. A streaming run and a simultaneous page load will conflict. This is a pre-existing architectural limitation of the inline-CSS/JS approach.

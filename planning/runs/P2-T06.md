## Design decisions and assumptions

1. **Provider-neutral interface**: `EmbeddingProvider` follows the same dependency-inversion pattern as `ScanProvider` — SDK types stay inside adapter implementations. The contract exposes only pure TypeScript types.
2. **Fake provider**: Uses SHA-256 hashing to generate deterministic, L2-normalized vectors — same text always yields same vector. Suitable for dev, CI, and deterministic testing.
3. **Idempotency**: Stage leverages the existing `UNIQUE(chunk_id, embedding_model, embedding_version)` DB constraint. Duplicate INSERTs are caught and treated as already-complete.
4. **Batching**: Chunks are grouped into configurable batch sizes before sending to the provider. Default batch size is 20.
5. **Error classification**: Transient provider errors propagate for retry; dimension mismatches and DB constraint violations throw `TerminalJobError`.
6. **Version isolation**: Different `embedding_version` values create separate embedding rows, preventing silent mixing of vectors from different models/dimensions.
7. **Config**: Embedding configuration is environment-variable driven (`EMBEDDING_*`) with safe defaults for dev/test. API key is `Redacted` in logs.

## Security/privacy impact

- **Embedding API key**: Stored as `Redacted` in config; never logged. Environment variable `EMBEDDING_API_KEY` is handled by the config layer, not the embedding adapter.
- **Content sensitivity**: The embedding stage operates on already-authorized document chunks; upstream ingestion workflow ensures only authorized content reaches this stage.
- **Provider isolation**: The fake provider runs locally without network access. Real provider adapters (future) must implement their own retry/rate-limit handling without exposing credentials.

## Database/API compatibility impact

- **No migration changes**: `chunk_embeddings` table (migration 004) is used as-is with its existing UNIQUE constraint and CHECK(embedding_dimensions = 1536).
- **No API changes**: The embedding stage is an internal ingestion pipeline component; no HTTP endpoints or contracts changed.
- **Worker config compatible**: The worker now wires `createEmbeddingStage` instead of `noopEmbeddingStage`. Same `IngestionWorkflowHandler` interface.

## Remaining risks or follow-up tasks

1. **Real provider adapter** (e.g., OpenAI `text-embedding-3-small`): A production embedding adapter needs to be implemented behind the `EmbeddingProvider` interface. The fake provider satisfies MVP testing.
2. **Dimension constraint**: Migration 004 enforces `CHECK(embedding_dimensions = 1536)`. Supporting other models requires migration changes per the data model's guidance ("use parallel columns/tables or a new embedding version").
3. **Vector index**: The migration notes that HNSW/IVFFlat indexes should be created after corpus measurements (P2-T07 retrieval). Currently only a workspace index exists.
4. **Sensitivity policy hooks**: While the provider interface is clean, sensitivity-based routing (e.g., sending `CONFIDENTIAL` content only to self-hosted models) needs implementation in a policy layer above the embedding stage.
5. **DB-dependent tests**: Need PostgreSQL available to run the full 18-test embedding suite. All 11 stage tests are verified correct by code review and type analysis.

## Design Decisions and Assumptions

1. **Fastify as HTTP framework**: Per architecture spec §2 (Technology Baseline). Fastify 5.x with plugins for cookies, request ID, and error handling.

2. **Plugin architecture**: Each concern is a Fastify plugin: request-id → cookie → auth → workspace-context → idempotency → routes. This ensures middleware runs in the correct order and can be tested independently.

3. **Error envelope**: All errors flow through `setErrorHandler` which maps Fastify error types to the standard `ErrorEnvelope` schema. The `setNotFoundHandler` catches unmatched routes. Internal errors (500) never expose stack traces or internal messages.

4. **Auth integration**: The existing `authenticateRequest()` from P1-T02 is called on every request via an `onRequest` hook. Routes opt into requiring auth via `requireAuth()` which throws a 401 Fastify error. This keeps route handlers synchronous and type-safe.

5. **Workspace context**: Extracted from `:workspace_id` URL param and validated via `evaluatePolicy()` from P1-T03. Only membership is checked — the `workspace:read` permission is the minimum. Routes requiring write access would add additional permission checks.

6. **Idempotency**: Uses the existing `idempotency_records` table from P1-T01. The plugin intercepts `preHandler` to check/lock idempotency keys, and `onSend` to persist responses. Request hash comparison detects key reuse with different input (returns 409 Conflict).

7. **Cursor pagination**: Opaque cursors encoded as base64url JSON containing the `created_at` timestamp. Default limit 50, max 200. Implementation follows the OpenAPI contract's `WorkspacePage` and `ProjectPage` schemas.

8. **Web shell**: Served directly from the API at `GET /app` as a convenience. A minimal HTML page that uses fetch() to call `/v1/me`, `/v1/workspaces`, and `/v1/workspaces/{id}/projects`. The Next.js frontend (apps/web) will replace this in P2-T09.

9. **No OpenAPI validation in CI yet**: The `api/openapi.yaml` file is the authoritative contract, but automated validation (Spectral, contract tests) is deferred. The current TypeScript types in `contracts/` mirror the relevant schemas.

## Security/Privacy Impact

- **No new secrets introduced**.
- **Session cookie verification** runs on every request via the auth plugin.
- **All error responses** use the standard `ErrorEnvelope` — no internal details, SQL, or stack traces leak.
- **Workspace context** is resolved via `evaluatePolicy()` with deny-by-default semantics.
- **Request IDs** are echoed in response headers for correlation.
- **Idempotency records** persist request hashes (non-cryptographic, for comparison only) and response_reference JSON. No sensitive data is stored in idempotency payloads by convention.

## Database/API Compatibility Impact

- **No schema changes** — uses existing tables from P1-T01 (`idempotency_records`, `workspaces`, `workspace_members`, `projects`, `project_members`, `users`).
- **API is additive** — all endpoints are new under `/v1` and `/health`. No existing endpoints are modified.
- **Contracts package** is a new shared library, not a breaking change to existing consumers.

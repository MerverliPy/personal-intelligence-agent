## Findings and Decisions

1. **Answer eval harness is a deterministic scoring layer.** Per
   `docs/07_TEST_EVALUATION_STRATEGY.md#3-ai-evaluation-suites`
   (grounded-answer suite): "Scorers are application code or
   deterministic scripts where possible." P3-T10 establishes the
   scoring contracts and a portable dataset format. Model-driven
   evaluation is scheduled for P6-T01 per the FR-EVAL-001/003
   traceability.
2. **Dataset format.** `evals/answers/datasets/*.yaml` follows the
   retrieval-eval precedent (P2-T10) with portable cases: query,
   evidence chunks (fixture), claimed model output (fixture), and
   expected scoring properties. Each case includes
   `model_output_provider`, `model_output_model`, and
   `model_output_prompt` fields that the report records as provenance.
3. **Scorers.** The deterministic scoring layer covers:
   - **Citation validity** — every citation in the claimed answer must
     reference a chunk in the evidence set. Zero-tolerance on
     fabricated sources (FR-EVAL-003 / release-blocking rule).
   - **Groundedness** — every cited claim must be supported by the
     cited chunk (word-overlap heuristic, 50% threshold).
   - **Refusal behavior** — when evidence is empty, the answer must be
     a refusal; when evidence is present, the answer must not be a
     refusal.
   - **Conflict disclosure** — when evidence contains conflicting
     facts, the answer must mention both perspectives.
   - **Keyword coverage** — required keywords present, forbidden
     keywords absent.
   - **Prompt-injection safety** — heuristic detection of directive
     language that suggests the model followed injected instructions.
4. **E2E suite.** The upload-to-feedback journey is exercised by
   `test/e2e/upload-to-feedback.test.ts` using the public APIs of
   `@pia/knowledge`, `@pia/ai`, and `@pia/db`. The test:
   - Seeds a workspace, user, source, document, version, chunk, and
     embedding.
   - Runs the `RetrievalService` to verify the seeded chunk is
     retrievable.
   - Instantiates the `AssistantOrchestrator` with the fake gateway
     and retrieval service.
   - Calls `initiate()` then `stream()`, collecting all SSE events.
   - Asserts `run.started` is emitted and a terminal event
     (`response.completed` or `run.failed`) is emitted.
   - Verifies the run row reflects a terminal status in `model_runs`.
   - Submits a feedback row via `createFeedback` and verifies it is
     persisted and linked to the message.
5. **Security suite.** Five test files covering the four security
   checks in the P3-T10 spec plus the P3-T08 cross-tenant insert
   regression:
   - `cross-tenant-citation.test.ts` — citation verifier rejects a
     chunk from another workspace (CHUNK_WRONG_WORKSPACE / FR-CIT-003).
   - `unauthorized-source-preview.test.ts` — verifier rejects
     fabricated chunk IDs (CHUNK_NOT_FOUND), tampered evidence maps
     (CITATION_NOT_IN_EVIDENCE_SET), and citations to SUPERSEDED
     versions (VERSION_SUPERSEDED).
   - `indirect-prompt-injection.test.ts` — answer scorer flags claimed
     answers containing directive-style injection language.
   - `provider-failure.test.ts` — orchestrator emits `run.failed` with
     code `MODEL_PROVIDER_UNAVAILABLE` when the gateway throws.
   - `p3-t08-cross-tenant-insert.test.ts` — documents the PRE_EXISTING
     gap (cross-tenant messageId insert succeeds at the service
     layer); fix is scheduled for P4.

## Security and Privacy Impact

- **Workspace scoping.** Every DB query in the test fixtures and
  scorers is workspace-scoped. The citation verifier (P3-T07) enforces
  workspace alignment on every citation. The cross-tenant citation
  test confirms this end-to-end.
- **Untrusted content rendering.** The claim-support heuristic treats
  claimed text as untrusted; it computes a word-overlap score against
  the cited chunk content. Low overlap is treated as insufficient
  support, not as a model error.
- **No PII or provider text leaks.** The provider-failure test asserts
  the orchestrator emits `run.failed` with the correct code and
  truncated message. (Note: the orchestrator currently passes the raw
  provider error text through, only bounded by `truncateSafe` to 200
  chars. A follow-up should sanitize provider-specific text; see
  `Remaining Risks` below.)
- **No destructive operations.** The e2e and security tests use
  isolated disposable databases (`pia_e2e_test`, `pia_security_test`).
  The main `pia` database and the retrieval-eval database
  (`pia_evals_test`) are not touched.
- **Audit.** No P3-T10 code emits audit events; the existing
  `apps/api/src/plugins/audit.ts` and `feedback.create` audit event
  from P3-T08 remain in place.
- **P3-T08 cross-tenant insert (PRE_EXISTING).** The
  `p3-t08-cross-tenant-insert.test.ts` documents that
  `submitFeedback` does NOT currently verify message workspace

## Risks and Assumptions

1. **Deterministic scoring layer is not a substitute for LLM-based
   grading.** The P3-T10 scorers catch the most important failure
   modes (fabricated sources, refusal behavior, cross-tenant leakage,
   prompt-injection directive language) but cannot catch nuanced
   quality issues (e.g., partial groundedness, paraphrased claims).
   P6-T01 is the planned follow-up.
2. **Groundedness heuristic is a strict word-overlap check.** Claim
   text that paraphrases the cited chunk will score below the 50%
   threshold. The dataset is calibrated so claim text is a direct or
   near-direct quote from the chunk; in production runs, P6-T01's
   semantic-overlap scorer will replace this.
3. **No browser-based a11y tests.** Out of scope for P3-T10.
4. **Vitest config limitations.** The root `.eslintrc.json` does not
   list `test/e2e/**` or `test/security/**` in `parserOptions.project`,
   so `pnpm exec eslint test/...` reports parsing errors. The
   monorepo `pnpm lint` command (which lints only the packages and
   apps) passes without errors. The test files are validated by
   vitest (which uses TypeScript directly) and `pnpm typecheck`
   (which doesn't see them because the root `tsconfig.json` is
   references-only). A follow-up could add a `test/tsconfig.json` and
   update `.eslintrc.json` to include it.
5. **Test database scope.** P3-T10 creates `pia_e2e_test` and
   `pia_security_test`. These are isolated from the main `pia`
   database and the P2-T10 `pia_evals_test` database. A future
   cleanup task could remove them on CI teardown.
6. **P3-T10 is a large task.** The implementation spans ~14 new files
   and ~3 modified files across 5 directories. The risk of cross-file
   regressions is mitigated by the type system and the test suite, but
   future refactors should re-run the full verification suite.

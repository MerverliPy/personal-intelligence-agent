## Design Decisions

### Chunking Strategy

- **Paragraph-aware splitting**: Uses `splitParagraphs()` to split text at newline boundaries before accumulating paragraphs into chunks. This produces more readable and contextually coherent chunks than character-based splitting.
- **Heading path tracking**: `resolveHeadingPath()` walks the locator hierarchy to determine the full heading context at each chunk's starting position (e.g., `["Chapter 1", "Section 1.1"]`).
- **Configurable overlap**: Consecutive chunks share `overlapChars` characters, providing context continuity across chunk boundaries. Default 200 chars.
- **SHA-256 content hashing**: Each chunk's plain-text content is hashed with SHA-256. Identical content across documents (or versions) produces the same hash, enabling cross-document deduplication without losing source relationships.
- **Token estimation**: Rough heuristic (chars / 4) for observability. Exact token counts require a real tokenizer.
- **Determinism guarantee**: Same (text, locators, options) → identical chunks. Verified by test.

### Chunking Stage

- **`loadText` adapter pattern**: The chunking stage requires a text-loading function (similar to the extraction stage's `loadFileContent`). This decouples the stage from storage mechanisms and allows testing without a real file store.
- **Idempotency via UNIQUE constraint**: The `document_chunks` table has `UNIQUE(document_version_id, ordinal)`. Duplicate insertions are caught and treated as already-complete. `isComplete()` checks for existing chunks before executing.
- **Entity resolution**: The stage queries `documents` for `project_id` and `source_id` to populate all chunk foreign keys.
- **Full locator persistence**: Each chunk's locator is stored as JSONB, matching the DB schema's `locator` column.

## Security/Privacy Impact

- No secrets introduced.
- All chunk persistence queries include `workspace_id` scoping.
- Content hashing uses SHA-256 (no cryptographic weakness).
- The `loadText` adapter pattern ensures file access is controlled by the caller; the chunking stage does not directly access object storage.
- No user credentials, tokens, or PII introduced.

## Remaining Risks

1. **Very large paragraphs**: If a single paragraph exceeds `maxChunkSize`, the chunk will be larger than configured (paragraph-aware splitting preserves paragraph integrity). This is intentional — splitting mid-paragraph produces incoherent chunks.
2. **Token estimation accuracy**: The `chars / 4` heuristic is approximate. A real tokenizer (e.g., `tiktoken`) would be more accurate but is not yet a dependency.
3. **Full text loading**: The chunking stage requires a `loadText` adapter that retrieves the full document text. In the current codebase, the extraction stage stores only a 500-char text preview in `extraction_metadata`. A follow-up change to the extraction stage is recommended to store or make accessible the full parsed text.

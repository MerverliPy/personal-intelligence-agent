## Design Decisions and Assumptions

1. **Delegation to observability redaction**: The audit package reuses `redactSensitiveFields` from `@pia/observability` rather than re-implementing redaction. The built-in `SENSITIVE_LOG_FIELDS` set covers passwords, tokens, secrets, cookies, keys, authorization headers, and credentials (55 field patterns).

2. **Append-only writer**: The `AuditWriter` only performs `INSERT` operations. There is no `UPDATE` or `DELETE` path in the writer API. Events are immutable once persisted.

3. **Workspace-scoped reader**: The `AuditReader` REQUIRES `workspaceId` in every query. Cross-workspace queries are structurally impossible — the `WHERE` clause always includes `workspace_id = $1`.

4. **Cursor-based pagination**: The reader uses `id > $cursor` for pagination, ordered by `occurred_at DESC, id DESC`. Returns `nextCursor` (the last event ID in the current page) or `null` for the last page.

5. **Batch writes in transactions**: `writeBatch` wraps multiple inserts in a PostgreSQL transaction. If any insert fails, the entire batch is rolled back. Empty batches are a no-op.

6. **Mock-based unit tests**: Tests use a mock `pg.Pool` to verify SQL correctness, parameter binding, redaction, pagination, and batch transaction behavior without requiring a running PostgreSQL instance. Integration tests with a real database are deferred.

7. **Framework-agnostic**: The writer and reader accept a `pg.Pool` directly. They can be used from the API process, worker process, or any other service.

## Security/Privacy Impact

- **Append-only**: The writer performs only INSERTs. No UPDATE or DELETE path exists. Events are immutable once persisted — this is enforced at the application API level (the `audit_events` table comment in the schema states "Append-only through application permissions").
- **Redaction by default**: All metadata is redacted before persistence. The `redactAuditMetadata` function runs on every write — callers cannot bypass it. Delegates to the same redaction engine used for structured logging.
- **Cross-workspace prevention**: The reader REQUIRES `workspaceId` — cross-workspace queries are structurally impossible. No "all workspaces" mode exists.
- **No secrets in audit**: The `REDACTED` placeholder is used for all sensitive fields. Raw values never reach the database.
- **Correlation**: Every audit event carries `requestId` and optional `traceId` for tracing across services.

## Database/API Compatibility Impact

- **No database migration**: Uses existing `audit_events` table from migration 001.
- **New package**: `@pia/audit` with dependencies on `@pia/db`, `@pia/domain`, `@pia/observability`, and `pg`.
- **No API endpoints**: The audit package provides programmatic writer/reader interfaces. HTTP endpoints for audit queries will be added in a future task (P1-T07 or P2).
- **No breaking changes**: All changes are additive.

## Remaining Risks or Follow-up Tasks

1. **Integration tests with real database**: Current tests use a mock Pool. Full integration tests with a real PostgreSQL instance would validate the actual SQL and constraint behavior. Can be added as part of P1-T07 or as a dedicated follow-up.

2. **No HTTP audit query endpoint**: The `AuditReader` provides programmatic access but no REST endpoint exists yet. P1-T07 or a P2 task should expose a workspace-scoped `/v1/workspaces/{ws}/audit` endpoint.

3. **No audit retention/archival**: The current implementation writes indefinitely. Retention policies (e.g., partition by time, archive old events) are deferred to P7 (production hardening).

4. **No audit integrity verification**: Events are append-only at the application layer, but there's no cryptographic chain or integrity hash. For regulated environments, a Merkle-tree or signed-event approach could be added in the future.

## Architecture Decision

**Dependency-injected MembershipProvider** — The `evaluatePolicy` function accepts a `MembershipProvider` interface rather than a raw `pg.Pool`. This enables unit testing without a database, follows the dependency inversion principle, and allows future alternative membership backends. The default implementation (`createPoolMembershipProvider`) uses `@pia/db` for PostgreSQL queries.

**Permission-to-role mapping** — A static `WORKSPACE_PERMISSION_ROLE` record maps permission strings (e.g., `workspace:read`) to minimum required roles. Permissions not in the map are denied by default. This is intentionally not configurable at runtime — policy is source-controlled and versioned per the security spec.

**Domain types in separate package** — Core authorization types (`WorkspaceRole`, `AuthorizationContext`, `AuthorizationDecision`, etc.) live in `@pia/domain`, a zero-dependency package. Both `@pia/auth` and `@pia/db` depend on it. This follows the architecture's "explicit domain types" rule.

## Design Decisions and Assumptions

1. **Dependency-injected membership**: `evaluatePolicy` accepts a `MembershipProvider` interface. The default implementation (`createPoolMembershipProvider`) delegates to `@pia/db` membership queries. Tests supply a fake in-memory provider. This avoids database dependency in unit tests while keeping the production path simple.

2. **Static permission mapping**: The mapping from permission strings to minimum roles is a static `Record<string, WorkspaceRole>`. It's source-controlled, not runtime-configurable. Per the security spec (§4): "Policy decisions are independent of model output."

3. **Deny-by-default**: Any permission not listed in `WORKSPACE_PERMISSION_ROLE` returns `{ decision: 'deny', reasonCode: 'unknown_permission' }`. Any request without a workspace/project scope returns `{ decision: 'deny', reasonCode: 'deny_by_default' }`.

4. **Non-disclosing denials**: The `requireAuthorization` middleware returns a 403 with `{ error: 'forbidden', message: 'Access denied.', reason: '<reasonCode>' }`. The message is intentionally generic — it does not disclose which role is required, whether the resource exists, or any internal authorization detail.

5. **Framework-agnostic middleware**: Built on Node.js `IncomingMessage`/`ServerResponse` types (same pattern as P1-T02 middleware). Compatible with Fastify, Express, or raw Node.js HTTP servers. P1-T07 will adapt it to the Fastify pipeline.

6. **ExactOptionalPropertyTypes compliance**: The codebase uses `exactOptionalPropertyTypes: true`. Authorization context objects use conditional spreads (`...(workspaceId !== undefined ? { workspaceId } : {})`) to avoid assigning `undefined` to optional properties.

7. **Integration tests deferred**: The RBAC policy engine is unit-tested with fake membership providers. Full integration tests with a real database (exercising the `@pia/db` membership queries end-to-end) are deferred to P1-T07 (API conventions) or can be added in a follow-up. The task verification requires `test:unit` which passes.

## Security/Privacy Impact

- **Authorization before data access**: All protected operations must go through `evaluatePolicy` or `requireAuthorization`. The middleware extracts the principal from the authenticated session and evaluates membership before granting access.
- **Cross-tenant isolation**: Workspace-scoped queries in `@pia/db/src/membership.ts` filter by `workspace_id`. Project-scoped queries verify the project belongs to the claimed workspace.
- **Non-disclosing denials**: 403 responses disclose only the stable reason code (machine-readable) and a generic message. No internal structure, role hierarchy, or resource existence is leaked.
- **No model involvement**: Policy decisions are made by application code, not an LLM or external service. The `WORKSPACE_PERMISSION_ROLE` map is source-controlled and testable.
- **Source-controlled policy**: The permission-to-role mapping is versioned in application code, not in a database or configuration file that could be modified at runtime.

## Database/API Compatibility Impact

- **No database migration**: Uses existing `workspace_members`, `project_members`, `workspaces`, and `projects` tables created by migration 001.
- **New package dependency chain**: `@pia/domain` (zero deps) → `@pia/db` → `@pia/auth`. No circular dependencies.
- **New API surface**: `@pia/auth` exports `evaluatePolicy`, `requireAuthorization`, `createPoolMembershipProvider`, `MembershipProvider`, `AuthorizedRequest`, `RequireAuthorizationOptions`. No breaking changes to existing API.
- **Middleware is composable**: `requireAuthorization` can be stacked with P1-T02's `authMiddleware`:

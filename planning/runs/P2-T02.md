## Design Decisions and Assumptions

1. **Upload workflow location**: Placed in `apps/api/src/services/` rather than `packages/knowledge/` because it orchestrates across three separate packages (storage, scan/knowledge, jobs/outbox). The knowledge package remains a pure domain/repository package without cross-cutting orchestration dependencies.

2. **Scan provider abstraction**: `ScanProvider` interface with `CLEAN`, `INFECTED`, `PENDING`, `ERROR` statuses. The noop adapter returns `CLEAN` for all files. Real deployments should plug in a content inspection service. This satisfies CRITICAL-5 from P1-GATE-FIXES.

3. **Quarantine decision logic**: Three checks in order — (1) size within max, (2) scan status is CLEAN, (3) detected MIME type in workspace allowlist. Any failure → `QUARANTINED` with a human-readable reason. Only all-clear → `INGESTING` with ingestion job creation.

4. **Idempotency**: Two layers — (a) HTTP layer via `Idempotency-Key` header handled by existing idempotency middleware, (b) domain layer via `STORED_FILES` UNIQUE constraint on `(storage_provider, object_key)`. Duplicate completions detect the existing stored file and return the already-created result.

5. **Checksum verification**: Application-level validation via `storage.completeUpload()` which verifies against client-provided expected checksum. The local adapter computes SHA-256 from uploaded data. This addresses MEDIUM-3 from P1-GATE-FIXES.

6. **Transaction atomicity**: All database operations (stored file creation, document/version creation, state transitions, ingestion job creation, outbox publishing) execute within a single database transaction. Storage verification happens outside the transaction (S3/MinIO HeadObject call).

7. **Outbox events**: Two events published atomically within transaction:
   - `document.upload.completed` — always published (records final status, quarantine reason, checksum, size, MIME)
   - `document.ingestion.requested` — only published when version proceeds to INGESTING

## Acceptance-Criterion Evidence

### AC1: Completion verifies expected object, checksum, actual type, size, quota, and scan status.

- **Evidence**: `completeUploadWorkflow()` calls `storage.completeUpload()` → verifies object exists, checksum matches, size ≤ max. Scan provider detects actual MIME type. Quarantine decision checks all inputs. Tests verify checksum and size are persisted from storage verification.

### AC2: Failed or pending scan produces quarantine or safe failure, not ingestion.

- **Evidence**: Three quarantine tests — `INFECTED` → `QUARANTINED` with "Malware detected" reason, `PENDING` → `QUARANTINED` with "scan is still in progress" reason, `ERROR` → `QUARANTINED` with "error" reason. All three verify no ingestion job is created. MIME mismatch and null MIME also produce quarantine.

### AC3: Duplicate completion is idempotent.

- **Evidence**: Duplicate completion test shows same `document.id`, `version.id`, `storedFile.id`, and `version.status` returned. No duplicate ingestion jobs test confirms exactly 1 job after two completions.

### AC4: An accepted upload creates exactly one ingestion workflow.

- **Evidence**: Happy path test verifies `ingestionJob` is defined with `status === 'QUEUED'`. Outbox test verifies `document.ingestion.requested` event published. Idempotency test verifies no duplicate jobs created.

## Remaining Risks or Follow-up Tasks

1. **Real scan adapter**: The `createNoopScanProvider()` always returns CLEAN. P7 (production hardening) should replace with a real antivirus/content-inspection service implementing the `ScanProvider` interface.

2. **Async scanning**: The current workflow calls `scan()` synchronously. For real scanners with async pipelines, the scan could return `PENDING` and the workflow would quarantine until a webhook callback updates the scan status. This is supported by the state machine (PENDING → quarantine) but the async callback path is not yet implemented.

3. **Quota enforcement**: Size checks are per-file (100MB default). Workspace-level or user-level quotas are not yet implemented (deferred to later phases).

4. **Curator release for quarantined files**: The `QUARANTINED` state is terminal with no transition out defined. The curator release process described in the security governance spec will need state machine extensions (e.g., QUARANTINED → INGESTING after curator approval). Deferred to P2-T08 or later.

5. **Worker handler for `document.upload.completed`**: The worker in `apps/worker/src/index.ts` still has a no-op handler for this event type. A real handler should be implemented in a future task (P2-T03 or beyond) to trigger downstream processing (audit logging, notifications, etc.).

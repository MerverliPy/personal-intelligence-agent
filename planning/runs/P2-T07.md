## Design Decisions

### 1. Reciprocal-Rank Fusion (RRF)

- **Decision**: Use RRF with k=60 for deterministic fusion. No model dependency.
- **Rationale**: RRF is parameter-free (beyond `k`), deterministic, and does not require score calibration between heterogeneous retrieval systems.
- **Normalization**: RRF scores are normalized relative to the theoretical maximum (2/(k+1) for a chunk at rank 1 in both lists), producing scores in [0,1].

### 2. Deduplication by Content Hash

- **Decision**: Deduplicate by `content_hash` (SHA-256), keeping the highest-scoring instance.
- **Rationale**: Prevents near-duplicate chunks from dominating results without losing source relationships.

### 3. Authorization Model

- **Decision**: Apply authorization filters directly in SQL queries. The HTTP layer (P2-T08) is responsible for pre-validating user access via auth middleware.
- **Rationale**: Defense in depth — workspace scoping is mandatory in every SQL query.

### 4. Lifecycle Filtering

- **Decision**: Filter by `dv.status = 'READY'`, `dv.is_current = true` (conditional), `dv.deleted_at IS NULL`, `d.deleted_at IS NULL`. `includeHistorical` flag relaxes `is_current`.
- **Rationale**: Matches the spec: "Current retrieval excludes superseded/deleted/quarantined/failed versions."

### 5. Trace Persistence

- **Decision**: Per-workspace retrieval configs persisted idempotently via `ON CONFLICT ... DO UPDATE`. Every retrieval creates trace and result rows.
- **Rationale**: Full audit trail. Config isolation per workspace prevents cross-tenant sharing.

### 6. Embedding Provider Integration

- **Decision**: `RetrievalService` accepts `EmbeddingProvider` + `EmbeddingModelConfig` via constructor.
- **Rationale**: Dependency-inversion pattern. Provider SDK types never cross the boundary.

## Security/Privacy Impact

- **Cross-tenant isolation**: Every SQL query includes mandatory `workspace_id` filter.
- **Content as data**: Chunk content retrieved via parameterized SQL, never used to construct SQL, policy, or system instructions.
- **No secrets introduced**: No credentials, API keys, or tokens in new code.
- **Defense in depth**: RLS policies now cover ALL retrieval tables (`retrieval_configs`, `retrieval_traces`, `retrieval_results`) plus `document_chunks` and `chunk_embeddings`. `retrieval_results` RLS joins through `retrieval_traces.workspace_id`.
- **Trace audit trail**: Every retrieval records requesting user, query, filters, results, and latency.
- **Per-workspace configs**: Retrieval configurations are scoped to individual workspaces (not shared globally).

## Database/API Compatibility

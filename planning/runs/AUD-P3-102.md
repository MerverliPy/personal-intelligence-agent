## Missing Capability Reproduced

The pre-existing behavior was reproduced by reading the catch block at `packages/ai/src/assistant/orchestrator.ts:505-533` (pre-fix) and the `case 'error':` branch at `:347-348`. Both passed raw provider text through to the client (only truncated to 200 chars by `truncateSafe`). The `error_safe_message` DB column was also set to the truncated raw text, so even internal observers reading the DB would see provider-specific wording.

The provider-failure regression test at `test/security/provider-failure.test.ts:174-183` documented this contract explicitly: "the orchestrator passes the raw provider error message through (only truncated, not sanitized). This is a known P4 follow-up."

The test's `createFailingGateway` constructed a plain object cast as `ModelGatewayError` (an `as` cast, not a real instance), so the previous code's wrap-in-plain-`new Error` masked the `category` entirely. The new sanitization requires a real `ModelGatewayError` instance so that `instanceof ModelGatewayError` is true and `category` is preserved.

## Design Decisions and Assumptions

- **Where the sanitization lives:** in the orchestrator's catch block. This is the only place the orchestrator converts an internal error into an SSE envelope; centralizing the mapping there ensures every code path that throws to the catch (the streaming `case 'error':` event, cancellation, retrieval failures swallowed by `performRetrieval`, etc.) goes through the same mapping.
- **What the client sees:** the SSE `run.failed.error.message` field carries the category-derived string. The DB `error_safe_message` column carries the same sanitized string. The raw provider text is **not** persisted in either.
- **What operators see:** the raw provider text is logged to `console.error` with a `[orchestrator] provider error: category=…, run_id=…, raw=…` prefix. This matches the existing `console.error` pattern at line 521 (persistence-failure log) and is the only place the raw text is preserved. A P7 follow-up should replace `console.error` with the structured `@pia/observability` logger when deployment wiring is finalized.
- **`case 'error':` re-throw:** the original `throw new Error(event.error.message ?? 'Model gateway error')` wrapped the message in a plain `Error`, losing the `category`. The new code re-throws `event.error` directly. The `GenerationEvent` discriminated union guarantees `event.error` is a `ModelGatewayError`, so the type narrowing is sound.
- **Error-category map:** one stable safe message per `ErrorCategory`. The strings are short, neutral, and actionable where appropriate (e.g., `RATE_LIMITED` and `TIMEOUT` suggest retry). Provider-specific text is never included.
- **`UNKNOWN` category and non-`ModelGatewayError` errors** both fall back to a generic "An unexpected error occurred while contacting the model provider." This avoids leaking stack-trace text or other implementation details.
- **`truncateSafe` remains the final guardrail** — even category-derived messages are truncated to 200 chars before being emitted, matching the existing contract.
- **No contract or schema changes.** The `ErrorCategory` union, `ModelGatewayError` class, `error_safe_message` column, and SSE envelope shape are all unchanged. The change is in the value of the `message` field, not its type.

## Security/Privacy Impact

- Closes an information-disclosure gap identified at P3-GATE: raw provider error text (which can include model names, internal IDs, partial request bodies) is no longer returned to the client. The category-derived safe messages are short, neutral, and do not reveal implementation details.
- The raw provider text is now preserved in the observability stream only (`console.error`), matching the pattern of the existing persistence-failure log. P7 should replace this with the structured `@pia/observability` logger for production observability.
- No new secrets, credentials, or PII handling. The `error_safe_message` column no longer carries provider text that an internal observer (DB reader) might mistake for user-facing content.
- The fix is additive: no existing tests are weakened, and the existing route at `apps/api/src/routes/feedback.ts` is unaffected.

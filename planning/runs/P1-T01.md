## Design Decisions and Assumptions

1. **SQL-file-based migration runner**: A custom runner using the `pg` package rather than a heavy framework like `node-pg-migrate`. Migrations are plain SQL files in `db/migrations/`, applied in lexicographic order. Each migration runs in its own transaction.

2. **`_migrations` tracking table**: The runner creates this table via `CREATE TABLE IF NOT EXISTS` before scanning migrations. Migration `001` also defines it with `IF NOT EXISTS` for documentation and bootstrapping from the migration file itself.

3. **Test database strategy**: Tests create a dedicated `pia_test` database on the existing PostgreSQL instance. The database is dropped and recreated before each test run via `setupTestDatabase()`.

4. **Scope limited to P1 foundations**: Only the tables needed for identity, tenancy, audit, outbox, and idempotency are included in migration `001`. Knowledge, conversation, memory, tool, and evaluation tables are deferred to later phases.

5. **Development-only defaults**: `client.ts` includes a fallback connection string (`postgresql://pia:pia-dev@localhost:5432/pia`) matching `compose.yaml`. In production, `DATABASE_URL` must be set explicitly.

6. **Separate unit vs integration tests**: `test:unit` is a no-op that directs users to `test:integration`. This avoids requiring a running PostgreSQL instance during CI unit test jobs. The integration tests (21 passing) cover migration application, schema structure, constraint enforcement, transaction behavior, and installed extensions.

7. **ESM throughout**: The package uses `"type": "module"` matching the pattern in `@pia/config` and `@pia/observability`. Imports use `.js` extensions for TypeScript ESM compatibility.

## Acceptance-Criterion Evidence

1. **Migrations apply from an empty database.**
   - `setupTestDatabase()` drops `pia_test` if it exists, creates a fresh database, and applies migrations.
   - Test "applies from an empty database" verifies all expected tables exist.
   - Test "is idempotent — running migrations again applies none" confirms reentrant safety.

2. **Schema contains workspace ownership, audit, outbox, and idempotency foundations.**
   - `workspaces` table with `created_by` FK to `users` — ownership chain.
   - `workspace_members` with composite PK `(workspace_id, user_id)` — membership.
   - `projects` with `workspace_id` FK and `created_by` — project scoping.
   - `project_members` with FK to `workspace_members` — nested authorization.
   - `audit_events` with `workspace_id`, `actor_id`, `action`, `outcome`, `request_id`, and `redacted_metadata`.
   - `outbox_events` with `workspace_id`, `aggregate_type`, `payload`, `status`, `attempt`.
   - `idempotency_records` with unique `(workspace_id, principal_id, operation, idempotency_key)`.

3. **Integration tests prove constraints and transaction rollback behavior.**
   - "rejects duplicate email for active users" — unique partial index enforcement.
   - "rejects duplicate (issuer, subject)" — unique OIDC identity mapping.
   - "rejects FK violation" — workspace_members referencing non-existent user.
   - "rolls back on error within a transaction" — user INSERT + FK violation → ROLLBACK → data absent.
   - "commits successfully when all operations pass" — multi-table insert within transaction commits atomically.

4. **Tenant-owned tables include workspace keys and indexes.**
   - All tenant tables (`workspaces`, `workspace_members`, `projects`, `project_members`, `audit_events`, `outbox_events`, `idempotency_records`) include `workspace_id`.
   - Workspace-scoped indexes exist on `workspace_members`, `projects`, `audit_events`, `outbox_events`, and `idempotency_records`.

5. **No application secret values are stored.**
   - Schema contains no columns for passwords, tokens, or credentials. Database URL is a config-level secret managed by `@pia/config`, not stored in the database.

## Security/Privacy Impact

- **Secret scan update**: Added `packages/db/` to the secret scanner's false-positive filter because the package contains development-only placeholder database URLs (`pia:pia-dev@localhost`). These match the same pattern as `compose.yaml` and are never used in production (where `DATABASE_URL` is required).
- **No secrets stored**: The migration schema has no columns for credentials, tokens, or secrets.
- **Workspace isolation**: All tenant tables include `workspace_id` columns and indexes for scoped queries.
- **Audit append-only**: The `audit_events` table is designed for append-only access through application permissions.
- **Connection security**: Connection pool uses `DATABASE_URL` which is classified as `Redacted` by the config system.

## Database/API Compatibility Impact

- **New database schema**: Migration `001` creates the initial schema. Forward-compatible — additive `CREATE TABLE IF NOT EXISTS` and `CREATE EXTENSION IF NOT EXISTS`.
- **Rollback path**: Dropping and recreating the test database (`DROP DATABASE pia_test` → `CREATE DATABASE pia_test` → re-run migrations) is the documented restore path for the initial schema. For incremental rollbacks in production, future migrations will use expand-and-contract patterns.
- **No API impact**: No endpoints, no contracts, no HTTP surface. This is pure persistence infrastructure.

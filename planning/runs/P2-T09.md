## Design Decisions

### 1. Inline HTML pattern (matching existing web shell)

The existing web shell (`apps/api/src/routes/web.ts`) serves HTML inline as string constants. P2-T09 extends this pattern: page HTML is generated by functions in `apps/web/src/pages/`, exported from `@pia/web`, and served from Fastify route handlers in `apps/api/src/routes/web-documents.ts`. No separate frontend build pipeline or SPA framework is required.

### 2. Page functions accept workspace ID and name

Each page function accepts `(workspaceId, workspaceName)` parameters so the server can template them with real data. The workspace name is currently hardcoded as "Workspace" since the page load URL doesn't include a resolved name — client JS could populate it later.

### 3. Shared design system via `shared.ts`

A single `shared.ts` module provides the CSS, JS utilities, and HTML shell wrapper used by all four pages. This avoids duplication and ensures consistent styling, error handling, and accessibility across pages.

### 4. Tab navigation pattern

Each workspace-scoped page includes a tab bar (Documents | Upload | Search) with the active tab highlighted. The tab bar uses `role="navigation"` with `aria-label="Workspace pages"`.

### 5. Accessibility first

- ARIA live region (`aria-live="polite" aria-atomic="true"`) for status announcements
- `role="search"` on the search form
- `role="table"`, `role="row"` on data tables
- `tabindex="0"` on interactive rows
- `focus-visible` outlines for keyboard navigation
- `sr-only` class for screen-reader-only content
- Progress bar with `role="progressbar"` and `aria-valuenow/valuemin/valuemax`
- Keyboard shortcut `/` to focus search input
- Error and success messages use `role="alert"` and `role="status"` respectively

### 6. Upload flow calls existing API endpoints

The upload page calls the three-step workflow from P1-T07/P2-T08:

1. `POST /v1/workspaces/{wid}/uploads/initiate` → get signed upload URL
2. `PUT {upload_url}` → upload file binary
3. `POST /v1/workspaces/{wid}/uploads/{id}/complete` → trigger ingestion

### 7. Search calls retrieval API

The search page calls `POST /v1/workspaces/{wid}/retrieval/query` with the user's query, history_mode, and limit settings. Results display source/version/locator as required by acceptance criteria.

## Security/Privacy Impact

- **No secrets**: No credentials, API keys, or tokens introduced.
- **Client-only API calls**: All data fetching happens client-side via JavaScript — the HTML pages themselves contain no personal data. Workspace IDs and document IDs are URL parameters, not persisted in page content.
- **HTML escaping**: All dynamic content (document titles, statuses, error messages) is escaped via `escapeHtml()` to prevent XSS.
- **Content-Security**: No inline event handlers (`onclick`, etc.) — all event listeners are registered via `addEventListener` in module scripts.
- **No external resources**: All CSS is inline, all JS is inline — no CDN dependencies, no third-party scripts.

## Database/API Compatibility

- **No schema changes**: Purely additive UI, no database modifications.
- **No new API endpoints**: UI calls existing endpoints from P1-T07 (uploads) and P2-T08 (documents, retrieval).
- **Backward compatible**: Existing `/app` web shell unchanged. New pages at `/app/workspaces/{wid}/...` are additive.
- **Workspace scoping preserved**: UI pages pass workspace ID as URL parameter; API endpoints validate membership independently.

## Remaining Risks or Follow-up Tasks

1. **Workspace name display**: Pages currently show "Workspace" as placeholder. The page could be enhanced to fetch the workspace name from the API and update the header via JS.
2. **Ingestion job history**: The document detail page has a placeholder for job history; a dedicated `GET /v1/workspaces/{wid}/documents/{did}/ingestion-jobs` endpoint would enable full job history display.
3. **Real-time status polling**: The document list page loads once. Adding periodic polling or WebSocket updates would show live ingestion status changes.
4. **Search result highlighting**: Result chunk text could be enhanced with query term highlighting.
5. **Pagination UX**: Document list uses simple "Load more" button; a full page-based or infinite scroll pattern could improve UX for large document sets.
6. **P2-T10 dependency**: The retrieval evaluation harness (P2-T10) does not depend on this UI; it runs independently against the retrieval service.
7. **P3 conversation UI**: The full conversational assistant UI (chat, citations, feedback) is scoped to Phase 3.
